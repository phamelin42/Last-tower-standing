# Installer sept skills Godot, ignorer le reste

> Étude du 26/11/2026, écrite avant la relecture complète de chaque skill : ce qui est installé fait foi dans `skills-lock.json` et la section « Skills de jeu tiers » du `CLAUDE.md`.

**Pour last-tower-standing, le meilleur rapport utilité/risque est un petit jeu de skills extraits de `gamedev-skills/awesome-gamedev-agent-skills` (Apache-2.0, 11,3 k étoiles, 16 skills Godot ciblant la 4.7) plus le skill `running-headless-godot` d'abagames, tous installables par `npx skills add … --skill <nom>` et copiés ensuite dans `.claude/skills/`.** Rien de ce qui a été trouvé ne couvre gdlint/gdformat de façon maintenue, ni un lanceur de tests maison comme `tests/lanceur.gd` : ce skill-là reste à écrire localement. Les serveurs MCP Godot (Coding-Solo, godot-ai, tomyud1, GDAI) exigent presque tous un éditeur graphique ouvert ou ajoutent du bruit par rapport à `godot --headless` ; aucun n'est recommandé pour un conteneur sans écran. Les « studios » d'agents (Claude-Code-Game-Studios, 40,9 k étoiles, 49 agents, 18 hooks) entrent en conflit avec le `CLAUDE.md` du projet et ses hooks : on y pioche au mieux trois agents de conception, copiés à la main. Tout ce qui est payant, à clé d'API ou à télémétrie par défaut est écarté d'office par la règle « pas d'appel réseau, de clé ou de SDK sans ADR ». **Limite majeure : aucun `SKILL.md` n'a été lu en entier pour les skills Godot, et aucune date de dernier commit n'a pu être vérifiée** (l'API GitHub était refusée pendant la recherche) ; il faut donc relire chaque skill avant de l'embarquer. Décisions que seul Phil peut prendre : accepter `npx skills` ponctuel dans un projet sans Node, et dire si Aseprite (payant) ou Blender sont envisageables.

### Comment installer

Le projet n'a ni Node ni npm, mais le conteneur cloud fournit Node (22.22.0 d'après le contexte commun, alors que le CLI `skills` demande 22.20+ ([GitHub](https://github.com/gamedev-skills/awesome-gamedev-agent-skills))). L'installation est donc un geste ponctuel, hors dépendance du projet : le résultat est un dossier de Markdown commité dans `.claude/skills/`. Les commandes, à lancer dans un clone du dépôt :

```
npx skills add gamedev-skills/awesome-gamedev-agent-skills --list
npx skills add https://github.com/gamedev-skills/awesome-gamedev-agent-skills --skill godot-gdscript
npx skills add https://github.com/abagames/agentic-gamedev-skills --skill running-headless-godot
```

La première liste les skills sans rien installer. Les deux suivantes reprennent la forme exacte donnée par skills.sh. Le dépôt propose aussi une installation en plugin Claude Code (`claude plugin marketplace add gamedev-skills/awesome-gamedev-agent-skills` puis `claude plugin install gamedev@awesome-gamedev-agent-skills`), mais cette forme installe les paquets entiers (`router`, `godot`, `unity`, `unreal`…) et, la note le signale, l'argument de marketplace n'est pas affiché en entier : **non vérifié**. Pour un contrôle fin du contexte chargé à chaque session, la copie par `--skill` ou à la main dans `.claude/skills/` est préférable. Le comportement exact du fichier `skills-lock.json` n'a pas été testé.

Avant de commiter : lire chaque `SKILL.md` et chaque `scripts/` (le projet interdit GUT et gdUnit, et la règle « rien téléchargé depuis GitHub » vise les dépendances de jeu, pas ces fichiers de guidage, mais Phil tranche, voir plus bas), ajouter dans la consigne que les réponses et textes visibles sont en français, et vérifier que le `CLAUDE.md` du projet l'emporte en cas de désaccord.

## Godot : beaucoup de skills, peu de maturité, aucun pour votre outillage

La collection d'awesome-gamedev-agent-skills (16 skills Godot : `godot-gdscript`, `godot-nodes-scenes`, `godot-signals-groups`, `godot-2d-movement`, `godot-tilemap`, `godot-physics`, `godot-ui-control`, `godot-animation`, `godot-shaders`, `godot-3d-essentials`, `godot-resources`, `godot-audio`, `godot-multiplayer`, `godot-export`, `godot-csharp`, `godot-gdscript-headless-testing`) est la plus adoptée. Elle comporte un encart de sponsor avec lien d'affiliation (la page assure qu'il n'influence pas le routage) ([GitHub](https://github.com/gamedev-skills/awesome-gamedev-agent-skills)).

**GodotPrompter** (`jame581/GodotPrompter`, MIT, 996 étoiles, 703 commits) est le plus profond : 59 skills dont `multiplayer-sync` et `dedicated-server`, 9 agents (`godot-code-reviewer`, `godot-game-architect`…), base Godot 4.3+ avec notes 4.5 à 4.8 ([GitHub](https://github.com/jame581/GodotPrompter)). Installation : `claude plugins marketplace add jame581/skillsmith` puis `claude plugins install godot-prompter@skillsmith`. Trois défauts pour ce projet : un hook `SessionStart` qui propose d'écrire dans les fichiers d'instructions (avec consentement), un coût de contexte de 59 descriptions, et un `godot-testing` centré sur GUT et gdUnit4, donc en conflit direct avec la règle du projet. Seuls ses agents de relecture et d'architecture seraient récupérables, à copier à la main.

**haxqer/godot-skill** (MIT, 259 étoiles) vise la 4.7 en headless (`run_project.py`, `lint_project.py`, `smoke_scenes.py`, `export_project.py`), mais embarque une trentaine de scripts exécutables dont `run_gdscript` qui exécute du GDScript arbitraire et `move_resource.py` qui réécrit les références du projet ([GitHub](https://github.com/haxqer/godot-skill)). Surface d'attaque et de dérive trop large pour un dépôt public : écarté, mais bon réservoir d'idées pour un script local.

Pour gdlint/gdformat, la seule référence trouvée est un skill `gdtoolkit` sur claudskills.com, dont le projet d'origine a désactivé gdtoolkit à partir de sa v0.3.4 à cause de plantages `NotImplementedError` dans `class_checks.py:144` ; le dépôt du skill n'est pas identifié ([claudskills.com](https://claudskills.com/skills/gdtoolkit/SKILL.md)). **Aucun skill maintenu ne traite gdlint/gdformat ni le lanceur maison** : un skill local `lanceur-godot` (commande, codes de sortie, conventions de test de `sim/` et `reseau/`) est à écrire avec `skill-creator`, déjà disponible.

### Serveurs MCP Godot : peu utiles sans écran

Coding-Solo/godot-mcp (MIT, 6,8 k étoiles, Node 18+) pilote le CLI de Godot, lance un projet et lit la sortie de débogage avec 14 outils ; il s'installe par `claude mcp add godot -e GODOT_PATH=/path/to/godot -e DEBUG=true -- npx @coding-solo/godot-mcp`. Le mode headless n'est pas documenté et la commande est en `npx` non épinglée ([GitHub](https://github.com/Coding-Solo/godot-mcp)). Il fait ce que `godot --headless` fait déjà, avec une dépendance Node en plus : non recommandé. `hi-godot/godot-ai` (MIT, 3,7 k étoiles, Godot 4.7+, 46 outils) exige l'éditeur ouvert avec son greffon, **envoie une télémétrie anonyme par défaut** (coupée par `GODOT_AI_DISABLE_TELEMETRY=true`) et peut réécrire un `.mcp.json` versionné ([GitHub](https://github.com/hi-godot/godot-ai)). `tomyud1/godot-mcp` (69 outils, éditeur graphique requis, ports locaux 6505 et 6510, modifications écrites sans annulation possible) et GDAI MCP (licence « All rights reserved », achat sur gdaimcp.com) sont également écartés ([tomyud1](https://github.com/tomyud1/godot-mcp), [GDAI](https://github.com/3ddelano/gdai-mcp-plugin-godot)). Aucun MCP ou skill officiel de la fondation Godot ou de W4 Games n'est apparu, mais la recherche n'était pas exhaustive.

## Conception de jeu : un seul dépôt engine-agnostic mérite l'installation

Le même dépôt gamedev-skills couvre 15 disciplines, 9 genres et 5 workflows : on y trouve `tower-defense`, `survival-crafting`, `game-ai`, `procedural-gen`, `level-design`, `game-jam`, `prototype-fast`, `game-docs` ([GitHub](https://github.com/gamedev-skills/awesome-gamedev-agent-skills)). Les deux échantillons lus (`tower-defense`, `game-feel`) sont concrets : valeurs numériques, pièges classiques, vérificateur exécutable. Ils ne citent ni MDA, ni les lentilles de Schell, ni Hodent. Il n'existe pas de skill dédié à la netcode (rollback, compensation de latence en Godot), ni au playtest, ni à l'équilibrage hors économie de tower-defense.

**Claude-Code-Game-Studios** (Donchitos, MIT, 40,9 k étoiles, 49 agents, 75 skills, 62 modèles, 14 règles, 18 scripts de hooks) a de vrais contenus d'experts : son agent `systems-designer` exige pour chaque formule une expression nommée, une table de variables, une plage de sortie et un exemple chiffré, et cite MDA, théorie de l'autodétermination, état de flow et types de joueurs de Bartle ([GitHub](https://github.com/Donchitos/Claude-Code-Game-Studios), [agent](https://raw.githubusercontent.com/Donchitos/Claude-Code-Game-Studios/main/.claude/agents/systems-designer.md)). Mais il s'installe en clonant le dépôt comme projet (`git clone … my-game`, puis `claude` et `/start`), impose son flux de travail et des règles de refus git qui peuvent bloquer des messages de commit anodins ; le dépôt admet que les routes Godot, Unity et Unreal sont moins éprouvées que la route web ([GitHub](https://github.com/Donchitos/Claude-Code-Game-Studios)). Les hooks entreraient en conflit avec ceux du projet (installation de Godot). Option raisonnable : copier à la main, licence MIT permettant, les agents `systems-designer`, `economy-designer` et `qa-lead` dans `.claude/agents/`, sans les hooks ; leur contenu de hooks n'a pas été lu, donc l'absence de télémétrie reste **non confirmée**. Le BMad Game Dev Studio (`bmad-code-org/bmad-module-game-dev-studio`, MIT, 284 étoiles) exige l'installeur BMad complet (`npx bmad-method install`) : écarté pour un projet mono-développeur déjà outillé.

Côté annuaires, les adoptions sont minuscules : sur claudemarketplaces, `godot-gdscript-patterns` (wshobson) affiche 32 installations sur 90 jours et le premier skill de jeu, Roblox, 117 ([claudemarketplaces](https://claudemarketplaces.com/best/skills/game-dev)). Les agrégateurs de masse (`sickn33/agentic-awesome-skills`, 3 000+ skills, avertissement que certains skills contactent des comptes externes ; `omer-metin/skills-for-antigravity`, contenu converti par IA) ne sont pas fiables sans lecture ([GitHub](https://github.com/sickn33/antigravity-awesome-skills)).

## Assets, art, audio et shaders : le local et gratuit d'abord

Le projet utilise le pack gratuit Tiny Swords et exige des assets libres avec crédits générés. Aucun skill ni MCP de suivi des licences Kenney ou OpenGameArt n'a été trouvé. Kenney met ses assets dans le domaine public ([Kenney](https://kenney.nl/support)) ; OpenGameArt attribue une licence par contribution (CC0, CC-BY, CC-BY-SA…), vérifiable fichier par fichier ([OpenGameArt](https://opengameart.org/collection/74690/CREDITS.TXT)). Un registre `credits.json` tenu à la main avec un test qui refuse tout asset sans entrée est un garde-fou simple à écrire localement et s'accorde avec la règle de Phil.

**Shaders** : sans clé ni réseau, `godot-shaders` (gamedev-skills) et `edemaistre/godot-shaders` (compilation par moteur de rendu en headless via `get_shader_uniform_list()`, environ 0,4 s par renderer, mais première apparition le 31 octobre 2026, 9 installations, cible macOS) sont les deux candidats Godot ([skills.sh](https://www.skills.sh/edemaistre/godot-expert-skills/godot-shaders)). `MiniMax-AI/skills` `shader-dev` donne des techniques GLSL ShaderToy (MIT) qu'il faut traduire en langage de shading Godot ([GitHub](https://github.com/MiniMax-AI/skills)). Aucun skill VFX/particules Godot n'a été trouvé.

**Audio** : `zaynabed/bfxr-mcp` (synthé bfxr2 embarqué sous MIT, `npm install`, `claude mcp add --scope user bfxr -- node "$(pwd)/src/index.js"`) génère des SFX en local ; sa clé `ANTHROPIC_API_KEY` est optionnelle et il est marqué « Inactive » sur Glama ([Glama](https://glama.ai/mcp/servers/zaynabed/bfxr-mcp)). Il introduit Node, donc un simple script Python local qui écrit des WAV serait plus conforme. **Art 2D** : pour du pixel art, aucun skill « Pillow pur, sans clé » n'a été confirmé par lecture ; `AnastasiyaW/claude-code-config` (« Pixel Art Studio », MIT, 217 étoiles) est à lire en premier, mais son chemin exact et ses dépendances sont non vérifiés ([GitHub](https://github.com/AnastasiyaW/claude-code-config)). ## Écarts et raisons de rejet

Les rejets sont de six sortes. **Clé payante ou service tiers** : `riccardogrin/creating-sprites` (clé OpenAI obligatoire), `SpriteCook/skills` (service payant, licence des sorties non indiquée), ElevenLabs, MiniMax, Pixellab, générateurs 3D de blender-mcp ([skills.sh](https://www.skills.sh/riccardogrin/skills/creating-sprites), [GitHub](https://github.com/SpriteCook/skills)). **Interface graphique requise** : godot-ai, tomyud1, GDAI, Blender, Krita, GIMP (seul `abelduarte/gimp-mcp` annonce un pont sans interface, non lu). **Télémétrie par défaut** : godot-ai et blender-mcp, toutes deux désactivables par variable d'environnement mais actives à l'installation. **Licence** : GDAI (« All rights reserved »), `bfollington/terma` en CC-BY-SA-4.0 (partage à l'identique inhabituel pour un skill), PIXL (« gratuit pour usage personnel », licence non nommée) ([terma](https://github.com/bfollington/terma), [PIXL](https://pixl-site.vercel.app/docs/MCP-Tools)). **Conflit avec les règles du projet** : tout skill centré sur GUT ou gdUnit4 (GodotPrompter `godot-testing`, Randroids-Dojo qui exige en plus un fork de Godot pour PlayGodot et est dépréciée ([GitHub](https://github.com/Randroids-Dojo/Godot-Claude-Skills))), les studios à hooks lourds (Donchitos), `htdt/godogen` (génération d'assets, GPU NVIDIA pour la 3D locale, API d'images payantes, démos de mars 2026 obsolètes selon son README ([GitHub](https://github.com/htdt/godogen))). **Fiabilité douteuse** : `alexcmd/godot` (un seul étoile, aucune licence, fichier de hooks annoncé défaillant sur tous les systèmes par un annuaire ([claudepluginhub](https://claudepluginhub.com/plugins/alexcmd-godot))), `zate/cc-godot` (URL d'installation factices, dépend d'un `godot-mcp` externe ([GitHub](https://github.com/zate/cc-godot))), `fernforestgames/agent-skill-godot` (12 étoiles, dépendances MCP annoncées par extrait de recherche seulement).

## Décisions qui reviennent à Phil

Quatre arbitrages ne sont écrits nulle part et ne doivent pas être devinés. Premièrement, **un skill copié est-il une dépendance au sens de la règle « rien téléchargé depuis GitHub » et des ADR ?** La lecture prudente est que `npx skills add` est un outil de développement qui dépose du Markdown et éventuellement des scripts Python (`td_curve_check.py`), sans dépendance d'exécution du jeu ; un ADR court, ou une ligne dans le `CLAUDE.md`, le dirait explicitement. Deuxièmement, **faut-il passer par `npx` dans un projet sans Node**, ou copier les dossiers à la main depuis un clone (même résultat, aucun `skills-lock.json`, aucune épingle de commit) ? Troisièmement, **où versionner ces skills** : dans le projet seul, ou dans `claude-context` pour tous ? Ce dépôt exige qu'une règle ne rejoigne le commun que si plusieurs projets l'utilisent ou si Phil le demande ; seul last-tower-standing est un jeu Godot, donc le projet seul est le choix par défaut, et il faut confirmer que `scripts/installer.sh` n'efface pas un dossier de skills local. Quatrièmement, **le budget de contexte** : le projet copie déjà environ 55 skills génériques surtout Angular, qui n'ont aucun rapport avec Godot ; ajouter sept à quinze skills alourdit chaque session, et il serait plus rentable de retirer du projet les skills Angular inutiles que de renoncer aux skills Godot. S'ajoute une question d'outillage payant : accepter ou non Aseprite pour du pixel art produit en conteneur (non recommandé tant que Tiny Swords suffit).

## Lacunes de la recherche

Aucun `SKILL.md` de skill Godot n'a été lu (seuls `tower-defense`, `game-feel`, `canvas-design`, `algorithmic-art` et un agent de Donchitos l'ont été) : la qualité réelle, l'absence de remplissage, la compatibilité avec gdlint, l'absence d'incitation à GUT ou à du code non typé restent à contrôler avant installation. **Toutes les dates de dernier commit sont non vérifiées** ; les seules dates connues sont les « premières apparitions » de skills.sh (27 juin 2026 pour `godot-gdscript` et `godot-shaders`, 17 mai 2026 pour `running-headless-godot`, 31 octobre 2026 pour `edemaistre/godot-shaders`) ; le dépôt gamedev-skills annonce « checked 2026-11-11 » sans preuve indépendante. Les étoiles viennent de pages résumées par un modèle et sont approximatives. Non testés : l'installation réelle, le comportement de `skills-lock.json`, la capacité de Coding-Solo à fonctionner sans éditeur, le fonctionnement réel du proxy à liste blanche pour `npx`, `uv` ou les téléchargements du CLI `skills`. Non cherchés : forums Godot et r/godot, retours d'utilisateurs, skills de netcode rollback, de playtest, de narration, de packing d'atlas ou de compression de textures, polices et art d'interface, équivalents d'autres moteurs au plugin officiel d'Unity. Le contenu des hooks de Donchitos n'a pas été lu, donc l'absence d'envoi de données reste à confirmer. Plusieurs licences (abagames, edemaistre, thedivergentai, popey, davila7, miles990 et d'autres) n'ont pas été lues.

## Conclusion

Le paysage se résume à un déséquilibre : l'écosystème de skills de jeu est abondant mais dominé par un dépôt (gamedev-skills) et un studio d'agents (Donchitos), tous deux auto-déclarés, alors que les besoins les plus spécifiques de last-tower-standing, un lanceur de tests maison et gdtoolkit, n'ont aucun skill. Le travail le plus rentable n'est donc pas d'installer davantage mais d'écrire deux skills locaux (lanceur de tests et conventions gdlint/gdformat) avec `skill-creator`, et un registre `credits.json` contrôlé par un test.

La règle « pas de dépendance sans ADR » ne bloque presque rien ici, car l'essentiel de ce qui vaut la peine tient dans du Markdown et un script Python local ; ce qui est bloqué par construction, ce sont les services à clé, les éditeurs graphiques et les hooks lourds. Prochaine étape : relire les sept `SKILL.md` retenus dans un clone jetable, noter ce qui contredit le `CLAUDE.md` du projet, puis seulement commiter.
